Forensic report · causal proof

ext4 superblocks exceed four raw images by 132,112,384 bytes

Root cause: a guest ext4 FITRIM tail discard reaches MicroSandbox v0.6.8's raw virtio-blk backend, then msb-imago 0.1.1 File::try_discard_by_truncate executes file.set_len(offset). That operation shortens disk.raw at the first free block of the final ext4 group while the ext4 superblock and in-memory virtual capacity remain unchanged.

This is not a formatter-size bug and not an MSW copy, backup, restore, resize, or migration bug. The formatter creates the full requested length. Corruption happens after attach, on an EOF-reaching virtio discard. A clean 2 GiB disposable volume reproduced the exact 132,112,384-byte mismatch; an otherwise identical no-FITRIM control retained delta 0.

1. Root-cause statement

Culprit Repository: superradcompany/imago, packaged as msb-imago 0.1.1, commit 2d9dfdec864e28f14e18c0d954ae8c471195f625. File: src/file.rs. Function: File::try_discard_by_truncate, released lines 818–838. Faulty operation: file.set_len(offset) at line 836.

Triggering input: any EOF-reaching VIRTIO_BLK_T_DISCARD or VIRTIO_BLK_T_WRITE_ZEROES range where offset + length >= cached_size. Triggering state: a writable raw image opened as a virtio-blk device. The observed fstrim proof follows DISCARD → discard_to_any; WRITE_ZEROES with UNMAP follows discard_to_zero, while WRITE_ZEROES without UNMAP follows write_zeroes. Both zeroing branches reach Raw::ensure_zero_mapping → File::pure_write_zeroes → File::discard_to_zero → try_discard_by_truncate. Observed command used for proof: fstrim -v /mnt/trimtest.

Ownership: the faulty function belongs to another tool, msb-imago. MicroSandbox v0.6.8 exposes it through pinned msb_krun_devices 0.1.25 and advertises virtio discard. MSW only creates and attaches the named disk; it does not compute or apply this truncation.

Historical-trigger limit: no retained request trace identifies the historical request kind, issuer, or time for the four images, nor why dev avoided a qualifying tail request. The base guest has an enabled, active, persistent weekly fstrim.timer, but the disposable boot had no automatic service journal entry. The deterministic reproduction used manual fstrim. The faulty operation, code path, boundary, and outcome are proven; historical attribution is not.

3. Why the deficit is exactly 132,112,384 bytes

inode table = 8,192 × 256 / 4,096 = 512 blocks final-group metadata = 1 block bitmap + 1 inode bitmap + 512 inode-table blocks = 514 blocks free tail = 32,768 − 514 = 32,254 blocks deficit = 32,254 × 4,096 = 132,112,384 bytes

The affected capacities are exact multiples of the 128 MiB ext4 block-group size. Their final groups are 479, 639, and 799, none of which is a sparse-super backup group. Read-only group-descriptor and block-bitmap inspection independently showed free_blocks=32,254, bits 0–513 allocated, and bit 514 as the first free bit. Every affected raw EOF is exactly:

last_group_start + 514 blocks
= declared_blocks - 32,768 + 514
= declared_blocks - 32,254

This is not a coincidental factorization. It is the exact start offset of the final FITRIM free extent. The imago function truncates to the discard offset, so EOF lands there.

4. Evidence chain from creation through corruption

  1. Creation is full-size. MicroSandbox v0.6.8 crates/image/lib/ext4/formatter.rs validates alignment, computes num_blocks = size_bytes / 4096, creates the file, and calls raw_file.set_len(options.size_bytes) before metadata writes. The reported 1 GiB create probe and the new 2 GiB disposable controls both had raw length equal to superblock length.
  2. MSW attaches the named raw disk. Current paths explicitly call msb volume create NAME --kind disk --size SIZE, then msb run ... --mount-named NAME:/path:kind=disk,size=SIZE. Historical implicit creation still reaches MicroSandbox's same materialize_volume_path formatter. The Aug 27 recovery record is direct historical proof: the freshly recreated playgrounds volumes passed volume_ext4_status with rc=0 immediately after creation at 17:41:11 UTC, then the recovery attached them, started the guests, and verified both ext4 mounts. The same current file births remain, so the later short EOF arose after successful creation rather than through replacement.
  3. MicroSandbox opens raw storage and advertises both operations. msb_krun_devices 0.1.25 Block::new opens ImagoFile, wraps Raw, derives virtio capacity, and advertises VIRTIO_BLK_F_DISCARD and VIRTIO_BLK_F_WRITE_ZEROES with their maximum request fields.
  4. Guest FITRIM emits an EOF-reaching discard. ext4 reports its final group free from block 514 through group end. fstrim sends that free extent through virtio-blk as VIRTIO_BLK_T_DISCARD.
  5. The released runtime routes the request to imago. The reproduced discard path is BlockWorker VIRTIO_BLK_T_DISCARD → DiskProperties::discard_to_any → SyncFormatAccess → FormatAccess → Raw::discard_to_any_unsafe → StorageExt::discard → File::pure_discard → File::discard_to_zero. The alternative VIRTIO_BLK_T_WRITE_ZEROES branches call discard_to_zero or write_zeroes; both reach the same File::discard_to_zero helper through raw zero mapping and File::pure_write_zeroes.
  6. imago truncates instead of punching a size-preserving hole. File::discard_to_zero first calls try_discard_by_truncate. For a range reaching cached EOF, it calls file.set_len(offset) and returns before macOS F_PUNCHHOLE, Linux FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, or the Windows size-preserving zero operation.
  7. Capacity becomes internally inconsistent. Neither imago's File.size nor Raw.size cache is updated. The live guest and msb volume inspect continue to report the original capacity while host EOF is shorter and the superblock remains unchanged. On reopen, the runtime sees the shorter file; ext4 mount fails with EINVAL.

Why the earlier 1 GiB probe was not enough

The reported 1 GiB probe stopped after creation, so it did not exercise the runtime discard path. In an additional disposable 1 GiB FITRIM run, final group 7 was a sparse-super backup group with 772 metadata blocks. It truncated by 131,055,616 B instead. The 2 GiB volume ends at group 15, a non-backup group with the same 514-block metadata prefix as the affected 60/80/100 GiB images, so it reproduces the exact contract delta.

All disposable sandboxes, volumes, and their stale lock files were removed at 2026-08-29 11:19:23 UTC. No existing managed image or managed sandbox was used by the experiment.

8. Minimal source fix

Fix imago, not MSW. Remove the EOF try_discard_by_truncate fast path from File::discard_to_zero, or otherwise prohibit a discard from changing Storage::size(). Route tail ranges through the existing size-preserving implementations:

  • macOS: fcntl(F_PUNCHHOLE)
  • Linux: fallocate(FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE)
  • Windows: the existing zero-data path

Deleting the truncate optimization is safer than truncating and re-extending. A failed second set_len would leave the same corruption. If hole punching is unsupported, the existing pure_discard contract already permits a no-op; capacity correctness must win over space reclamation.

Then release msb-imago, bump MicroSandbox's pinned dependency, rebuild the runtime, and require that fixed MicroSandbox version for raw writable disk volumes.

9. Regression tests

Required unit contract in imago

  1. Create a private 16 MiB sparse file and open it through imago File and Raw.
  2. Issue discard_to_any for the final aligned 4 MiB.
  3. Assert OS metadata length, File::size(), and Raw::size() all remain 16 MiB.
  4. For discard_to_any, assert only the three length invariants. Add separate EOF-reaching discard_to_zero and write_zeroes cases that assert zero read-back and unchanged length; allow a no-op only for pure discard when unsupported.

Before the fix, the host metadata assertion reads 12 MiB while the caches still read 16 MiB. After the fix, all three remain 16 MiB. This directly guards the broken invariant.

Required MicroSandbox behavioral integration

  1. msb volume create ... --kind disk --size 2G.
  2. Attach it as writable raw ext4 to a disposable sandbox.
  3. Run fstrim -v on that mount.
  4. Stop the sandbox and assert stat(disk.raw).len == capacity_bytes == superblock_blocks × block_size.
  5. Restart and assert the ext4 mount succeeds.

Use 2 GiB, not 1 GiB, so the final group is a non-sparse-super group and the regression exercises the exact 514-block metadata boundary seen here. This test fails on v0.6.8's pinned runtime and passes only when the runtime discard operation preserves logical size.

10. Disposition of the recent MSW defensive correction

Replace the fresh-volume extension behavior; retain fail-closed geometry validation.

  • Remove the strict fresh-only conditional ftruncate extension once MSW requires a MicroSandbox build containing the imago fix. The formatter already creates exact length, and post-create extension does not protect against a later FITRIM truncation.
  • Retain read-only raw/ext4 geometry validation before attach and on later starts. It detected this corruption and prevents mounting an internally inconsistent image. Detection is not speculative repair.
  • Do not extend existing affected images automatically. Their recovery remains a separate offline data-integrity decision.
  • Until a fixed runtime is installed, the current fresh correction is not a durable solution. The actual faulty operation remains reachable after attach.

11. Conclusion

The causal chain is demonstrated end to end. The exact number is ext4's final non-backup-group free tail. MicroSandbox v0.6.8 correctly formats a full sparse file, then its virtio discard path reaches an imago optimization that mistakes “discard to device end” for permission to shrink the backing file. The same helper is also reachable from WRITE_ZEROES. The minimal correction is to preserve raw image logical length during both operations, then regression-test FITRIM and restart. No retained request trace identifies the historical request kind, issuer, or time, nor why dev avoided a qualifying tail request; the enabled timer is plausible but is not attributed.
