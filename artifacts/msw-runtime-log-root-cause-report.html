MSW Monitor · Runtime log investigation

Three different failures share one missing boundary.

Provisioning, health checks, and Monitor queries run inside guests, but their sessions are captured as if they were user workload logs. One stale transport process then turns a missing runtime file into an endless visible retry storm.

Decision: fix lifecycle reconciliation and session provenance upstream. UI string filtering would hide symptoms, delete legitimate user output, and leave the broken relay and partial workspace configuration intact.
Live evidence collected: all three workspaces reported Running with systemd as PID 1; the relay file was absent in every guest; the bounded log contained 197 missing-relay failures from 197 personal sessions at a mean 8.96-second interval; only personal had an orphaned shuttle process. These observations came from the live runtime, not MSWMonitor’s deterministic UI fixtures.

Issue-by-issue findings

1

Missing GitHub relay retries forever

personal prints a Python ENOENT about every nine seconds.

What is happening

Shuttle.spawn_relay executes python3 /var/lib/msw-runtime/msw-github-relay.py inside the workspace. The file is missing, so the child exits immediately. Shuttle.run respawns it; the backoff caps at eight seconds, producing the measured cadence.

Why it is wrong

This is a permanent precondition failure treated as transient. It wastes sessions, evicts useful records from the bounded log, floods the UI, and never repairs GitHub transport. A log viewer cannot make this healthy.

Root cause

Relay installation occurs only during provisioning. Startup accepts a matching live shuttle without checking that the guest relay exists or matches the expected hash. Semantic policy no-ops skip transport checks; empty policies do not remove stale shuttles. The orphaned personal shuttle survived with parent PID 1, while dev and playgrounds had no shuttle, explaining the workspace difference.

Evidence boundary

The investigation proved the relay is absent in all three guests and found the orphaned process. Retained evidence cannot prove what deleted the files or originally orphaned that process.

Permanent fix
  1. Add one idempotent transport reconciler after app startup, workspace create/recreate/start, repair, and every policy application, including semantic no-ops.
  2. For active policies, verify workspace stability, relay existence and hash, install atomically on drift, verify Git configuration, own exactly one shuttle, and require an end-to-end heartbeat before reporting provisioned.
  3. For empty policies, stop owned children and remove stale PID, signature, plist, and LaunchAgent state.
  4. Classify a missing relay or hash mismatch as permanent MSW_RELAY_NOT_INSTALLED: open the retry circuit and emit one repair action. Reserve jittered exponential retry for transient sandbox or transport failures; reset only after a verified heartbeat.

Primary code: lib/msw-github-shuttle.py:51–58, 111–133, 210–213, 382–418; bin/msw:3687–3720, 3869–3875, 7527–7541, 8112–8164.

2

Systemd commands run before systemd is ready

The message says the image lacks systemd, but the verified guests do use systemd as PID 1.

What is happening

Bootstrap creates a configured workspace, then immediately runs guest configuration. hostnamectl is the first systemd client, followed by systemctl. There is no readiness barrier after msb run.

Why it is wrong

The error is both alarming and misleading: it looks like a permanently incompatible image, but it is a startup race. Worse, the configuration is recorded before guest setup succeeds, so retries can skip a partially configured workspace.

Root cause

The newer bootstrap path omitted the readiness wait already present in setup.sh. Its transaction order is also wrong: workspaces.json is committed before configuration completes, and an existing sandbox is later treated as complete.

Producer certainty

hostnamectl is the leading producer because it runs first and set -e ends the session. This remains an inference because current log records omit argv. The missing startup seam and early commit are verified.

Permanent fix
  1. Poll a silent PID-1 and systemd-bus readiness predicate with a bounded deadline before any systemd client.
  2. Journal per-workspace configuration stages and make every guest configuration step repeatable.
  3. Commit workspace configuration only after all steps pass verification. On failure, restore the previous lifecycle and retain an explicit needs-configuration state.
  4. Report a typed, retryable startup timeout in internal diagnostics, not raw guest stderr in workload logs.

Call chain: BootstrapCoordinator.swift:974 → MSWClient.swift:686–700 → bin/msw:8719–8793 → bin/msw:8597–8717 → bin/msw:8493–8531. Existing correct wait: setup.sh:459–470.

3

Monitor control responses appear as user logs

Empty directory JSON, standalone [/], and storage probes are successful internal operations, not workload events.

What is happening

Opening or refreshing workspace Files triggers a guest directory query, which prints compact JSON. Repository refresh prints a JSON array incrementally, so empty results become separate bracket writes. MicroSandbox captures every guest exec write; the log adapter marks every valid unrecognized record safe for display.

Why it is wrong

The UI gives successful RPC responses no operation label or context, so users read them as application output or corruption. Filtering literal [] or JSON would also delete legitimate user logs.

Root cause

Guest sessions carry no reliable origin or visibility metadata. Control-plane and workload output share one undifferentiated capture stream, and the adapter defaults unknown records to visible.

The ext4 line

workspace=ext4 runtime=ext4 came from an ad hoc findmnt verification command in an earlier Smithers execution, not tracked application code. It leaked into the same log because the underlying session-origin boundary is missing.

Permanent fix
  1. Add structured session-origin metadata, or a first-class internal/no-capture execution mode, at the MicroSandbox/MSW boundary.
  2. Tag directory, repository, setup, storage, health, and relay sessions as control-plane; tag user processes as workload.
  3. Default the Logs tab to workload records. Put typed internal diagnostics behind an explicit disclosure with operation name, result, and repair action.
  4. Preserve unknown user payloads verbatim. Never classify by message content.

Directory chain: DetailView.swift:889–942, 1013–1053 → AppModel.swift:1354–1435 → MSWClient.swift:218–255 → bin/msw:6127–6243, 6301–6352. Repository chain: DetailView.swift:186–199, 243–249 → AppModel.swift:1850–1879 → MSWOperationService.swift:47–51 → MSWClient.swift:204–215 → bin/msw:7855–8069.

4

Clock-only timestamps make correct ordering look wrong

Rows can be sorted correctly while appearing chronologically reversed.

What is happening

The app sorts by the full Date, then renders and copies only HH:mm:ss. Logs spanning midnight or several days therefore lose the date that explains their order. Shuttle output also writes clock time only.

Why it is wrong

A user cannot distinguish “today at 10:25” from “yesterday at 19:55.” The presentation contradicts the underlying order and copied evidence is ambiguous.

Permanent fix

Add day separators or render a date whenever results span calendar days. Always copy an ISO 8601 timestamp with date and offset. Keep compact clock time only for a single-day visible range.

Presentation: DetailView.swift:665–700, 716–740. Shuttle: lib/msw-github-shuttle.py:71–73. Existing timestamp-preservation tests: AppModelTests.swift:860–906; multi-day rendering is uncovered.
