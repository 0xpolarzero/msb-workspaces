MSW Monitor · Proposed architecture

GitHub authorization that feels like Vercel

Authenticate once in GitHub, return to MSW Monitor, choose which workspaces receive which repositories, and review the exact access before applying it.

Status Proposed Current commit 58738d4 Scope OAuth UX + credential isolation
Why this plan changes the current design. The current app exposes six client-ID fields and separate guest/host Device Flow buttons. More importantly, CredentialBroker stores the full GitHub user token per workspace; repositoryIDs are metadata used for selection and verification, not token down-scoping. A single public client ID plus per-VM checkboxes would improve UX but would not create strong VM isolation.

Decision

One visible login

Use a hosted MSW Connect OAuth broker so the desktop app can provide a real browser callback and a single GitHub authorization session. No GitHub client secret is shipped in the Mac bundle.

Per-workspace grants

After authentication, the user assigns installations and repositories to dev, playgrounds, and personal. Each assignment gets its own grant and access mode.

Server-minted tokens

The service keeps the GitHub App private key server-side and mints short-lived installation tokens restricted to the selected repository set. VMs never receive the full GitHub user token.

Fallback if a hosted service is rejected: retain distinct GitHub App identities for every isolation boundary and orchestrate the required prompts. Do not collapse to one client ID while treating repository metadata as enforcement.

  1. Click Connect GitHub. MSW opens the hosted authorization page in the system browser or ASWebAuthenticationSession.
  2. Authorize the MSW GitHub App once. The callback returns a one-time authorization result to the desktop app through a registered callback or loopback listener.
  3. Show the signed-in account and available GitHub App installations. If the App is not installed for an owner, offer Install MSW App as the next step.
  4. Present a workspace assignment view. Each workspace card has owner, repositories, and an explicit Read-only / Read + write choice. Read-only is the default.
  5. Show a final review and apply all assignments together. The app reports exactly what each VM will receive and what remains unconfigured.

Invariant: repository selection must be enforced at token issuance, not only stored in repositoryIDs. A VM receiving a broad user token defeats the assignment UI.

Access semantics

  • “Read-only” maps to the guest credential path.
  • “Read + write” maps to the host credential path and requires an explicit user choice.
  • Each workspace receives an independent grant and token renewal path, even when the user authorizes once.
  • Disconnecting a workspace revokes its grant and removes its local Keychain material; disconnecting the account revokes all associated workspace grants.
  • GitHub App revocation or installation removal invalidates affected grants and marks the workspace as needing authorization.

Implementation phases

1 · Service contract

  • Define OAuth start, callback, session, installation discovery, repository discovery, grant creation, token renewal, and revocation endpoints.
  • Use state, PKCE, one-time callback codes, strict redirect allowlists, rate limits, and token redaction.
  • Use the GitHub App private key only on the service to mint installation tokens.

2 · Desktop authorization client

  • Replace the visible Device Flow/client-ID plumbing with one production-configured Connect action.
  • Implement callback handoff, session cancellation, expiry, retry, and account display.
  • Keep Device Flow only as an explicit development fallback if the service is unavailable.

3 · Workspace assignment UI

  • Replace guest/host buttons with workspace cards and a single assignment review.
  • Support owner, repository multi-select, access mode, verification repository, and per-workspace remove/re-authorize.
  • Remove the six client-ID fields from Settings; Settings should show connection state and access assignments only.

4 · Credential migration

  • Advance the broker metadata schema from v2 to a grant-based schema.
  • Stop writing full GitHub user tokens into per-workspace records.
  • Replace local refresh-token handling with grant renewal and installation-token retrieval.
  • Require explicit reauthorization for existing broad-token records; do not silently claim they are repository-scoped.

5 · MSW/VM delivery

  • Make MSWClient request credentials by workspace grant, not by arbitrary local token metadata.
  • Pass only the selected short-lived token to the target VM or use a brokered credential proxy.
  • Preserve host write approval and guest read-only sequencing.

6 · Observability and rollout

  • Add revocation, expiration, and grant-audit events without recording tokens or repository secrets.
  • Ship the service behind a staging GitHub App first.
  • Roll out reauthorization with a clear migration screen and a safe rollback for unassigned workspaces.

Verification plan

  • Mock OAuth callback rejects missing, mismatched, replayed, and expired state.
  • Mock GitHub discovery cannot assign an installation or repository outside the authenticated account.
  • Token issuance tests prove a requested repository subset is enforced by the issued installation token.
  • Credential broker tests prove no full user token is written to workspace metadata or passed to a VM.
  • Separate workspace grants cannot read or renew one another's credentials.
  • Read-only and read/write permissions are distinct, with write access opt-in.
  • Disconnect, GitHub revocation, installation removal, token expiry, and service outage produce recoverable UI states.
  • Setup UI tests cover Connect, callback success, installation selection, VM assignment, review, apply, reauthorize, and cancel.
  • Add a success-path BootstrapCoordinator.run() integration test with injected setup, authorization, verifier, and host-service fakes; also exercise Continue in a controlled first-run environment before declaring the end-to-end setup path complete.
  • Run the canonical build, unit tests, and UI smoke test; manually verify the browser handoff and the final assignment summary without real credentials in test artifacts.

Acceptance criteria

  • A new user sees one clear Connect GitHub action, not client-ID configuration.
  • One GitHub authorization can assign access to multiple MSW workspaces.
  • The user can see and review every owner, repository, workspace, and access mode before applying.
  • Repository checkboxes correspond to enforced server-side token scope, not metadata-only promises.
  • No GitHub client secret, private key, or broad user token ships to or is logged by the desktop app or VM.
  • Existing workspace credentials migrate explicitly and safely; broad existing tokens are never relabeled as scoped.
  • Users can revoke one workspace without disconnecting every workspace.
