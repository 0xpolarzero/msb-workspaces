MSW · Product and architecture recommendation

Yes, a macOS, Linux, and Windows app is possible.

MicroSandbox itself now supports local hosts on all three operating systems. The important constraint is that the current MSW product does not: its installer, CLI integrations, credential handling, background services, and SwiftUI application are deliberately macOS-specific. The right move is a new cross-platform shell over a portable core—not a line-by-line port of the current app.

Recommendation: Tauri 2 UI: React + TypeScript + Vite Core: Rust Windows: beta while MicroSandbox is preview

Executive decision

Build it, but separate “MicroSandbox support” from “MSW support.” MicroSandbox documents local operation on glibc Linux with KVM, Apple-Silicon macOS, and Windows 11 with Windows Hypervisor Platform. Windows is explicitly preview.

Use one Tauri desktop app and one portable Rust domain/runtime layer. Keep the browser-like UI unprivileged. Put all process execution, secrets, filesystem mutation, and host integration behind narrow typed Rust commands. Implement small OS adapters for the unavoidable differences.

The release promise

macOS: supported, Apple Silicon only for local MicroSandbox.

Linux: supported, glibc distribution and working KVM required.

Windows: beta, Windows 11 + WHP; the underlying runtime is preview.

Do not market Intel macOS or Windows GA until the runtime supports that promise.

Recommended stack

Tauri 2 + React/TypeScript + Vite

  • Tauri 2 supplies native windows, tray menus, packaging, signed updates, and a Rust boundary on macOS, Linux, and Windows.
  • React + TypeScript + Vite is the boring, well-supported UI choice. Avoid Next.js: this desktop app does not need a server framework.
  • Rust owns commands, lifecycle state, schema validation, process control, cancellation, filesystem access, credentials, and platform adapters.
  • MicroSandbox msb stays the VM runtime. Ship a pinned per-target binary as a Tauri sidecar when distribution rights and signing permit; otherwise download a signed artifact during setup and verify its manifest before use.
  • Generated TypeScript types come from the Rust protocol schema. Do not maintain parallel handwritten Swift/Rust/TypeScript models.

Why not the obvious alternatives?

Electron: fastest for a JS-only prototype, but it ships Chromium/Node and expands footprint and process capability.

Flutter: strong custom UI, but adds Dart and does not reduce the native host-integration work.

Avalonia: credible if the team is already strong in C#/.NET; otherwise it introduces the same language transition with less alignment to the existing web ecosystem.

Three native apps: best native feel, worst long-term duplication. Not justified here.

Architecture

One UI and one domain model. Platform-specific code exists only at host boundaries. The existing typed msw app … --format json surface is a useful contract to preserve while the shell implementation is replaced.

React UI
Setup, dashboard, workspace detail, logs, settings. Renders state and sends typed intents. No shell access, no credential access, no arbitrary path execution.
↓ typed Tauri commands and events
Tauri command API
Narrow allowlist: doctor, list_workspaces, start, stop, inspect, stream_logs, open_workspace, configure_access. Validate every ID, path, URL, and transition in Rust.
↓ domain operations
msw-core
Portable Rust library: lifecycle state machine, freshness semantics, action planning/confirmation, protocol envelopes, redaction, cancellation, resource policy, GitHub policy, and recovery rules.
↓ traits, not conditionals spread through the app
Host adapters
macOS
Keychain, launchd/ServiceManagement, native URL/file open, Apple-Silicon preflight.
Linux
Secret Service, systemd user services, xdg-open, KVM and group/device checks.
Windows
Credential Manager, WHP/firmware checks, Windows service or per-user startup task, ShellExecute, firewall guidance.
↓ fixed argv + bounded JSON/JSONL
MicroSandbox
msb runtime. Pin and verify version/architecture; consume machine-readable output; never parse human tables; bind published ports to loopback by default.

Security boundary

Never give the webview a general shell

Tauri can execute sidecars, but JavaScript should not receive the shell plugin or broad argument permissions. Rust constructs executable paths and argument arrays from validated typed inputs. This keeps a UI injection bug from becoming arbitrary host command execution.

Keep the current trust semantics

  • Unknown or stale runtime state never becomes “Stopped.”
  • Destructive actions use plan → review → apply with expiring plan IDs.
  • Credentials remain in the host credential store and never enter logs, argv, preferences, or the webview.
  • Bounded JSON/JSONL, schema versions, output limits, and redaction remain mandatory.

Build order

Prove runtime parity before investing in pixel parity. Keep the current macOS app operational until the new app reaches its contract.

  1. Platform spikeOn one real host per OS, run msb doctor, create/start/inspect/stop a sandbox, publish a loopback port, stream bounded logs, and update the runtime. Record unsupported behavior. Windows remains beta if preview limitations surface.
  2. Freeze the app protocolTurn the current msw app JSON envelopes into versioned schemas and golden fixtures. Define capability flags so unsupported features are hidden or disabled honestly, never guessed from the OS name.
  3. Extract msw-coreMove state transitions, plans, validation, redaction, and MicroSandbox process control into portable Rust. Keep platform integrations behind traits. Do not keep growing the Bash CLI as the cross-platform core.
  4. Build the thin Tauri shellShip Setup, Monitor, workspace detail, logs, Settings, tray actions, and one clear recovery surface. The UI consumes state; it does not own state.
  5. Implement adapters in risk ordermacOS parity first, Linux second, Windows third. Credential storage, background services, host networking, browser/terminal opening, and update/install flows each need native implementations.
  6. Package and sign per OSBuild on native runners or machines. Produce macOS app/DMG with signing and notarization, Linux AppImage/deb/rpm as chosen from tested distributions, and signed Windows MSI/NSIS artifacts. Sign updater payloads independently.
  7. Promote by evidenceUse unit tests with a fake msb, protocol contract tests, and semantic UI smoke tests on each OS. Add dedicated hardware canaries for KVM, Apple virtualization, and WHP; ordinary CI without nested virtualization cannot prove local VM behavior.

First shippable contract

Include

  • Prerequisite check and actionable repair instructions.
  • Create/import the three workspaces.
  • Truthful state, freshness, CPU/memory/disk, and published ports.
  • Start, stop, restart, open terminal, open browser port.
  • Bounded logs and redacted diagnostics.
  • Tray quick actions and signed app/runtime updates.

Defer until the base is proven

  • Cross-platform GitHub credential proxy parity.
  • Privileged automatic host repair on every distribution.
  • Backup/restore across OS families.
  • Embedded terminal emulation.
  • Cloud/local seamless migration.
  • Windows GA while MicroSandbox itself remains preview.

Bottom line

The project is viable. MicroSandbox has the necessary host coverage. The clean path is Tauri 2, a React/TypeScript UI, a Rust core, and three narrow host adapters. Treat Linux as a supported target after its real-host canary passes. Treat Windows as beta while MicroSandbox calls Windows support preview.

The first engineering action should be the three-host runtime spike and protocol freeze—not a UI rewrite. If those pass, the architecture above gives one convenient codebase without pretending that credentials, services, virtualization setup, packaging, and networking are identical across operating systems.
