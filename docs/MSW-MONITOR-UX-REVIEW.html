MSW Monitor · Product UX review

Make every workspace action trustworthy, recoverable, and obvious.

The app has a solid native foundation, but it is not yet a best-in-class operational experience. The next gains are not ornamental: users need one truthful health model, explicit workspace scope, reviewed destructive actions, real operation progress, recovery paths that tell them exactly what to do next, and opt-in alerts when the app is hidden.

Review date: 2026-08-11 8 parallel Sol audits Read-only source review Native macOS app

Executive verdict

Prioritize trust before polish. The monitor can say “Ready” before a real workspace baseline exists, can present destructive GitHub revocation as a one-click action, and can show operation success before authoritative reconciliation. Those are product-level trust breaks. Fix them before investing in more panels, decorative treatment, or lower-frequency capabilities.

The existing fail-closed model and transactional services are a strong base. The UX currently hides too much of that safety logic: quarantine reasons, freshness, server capability limits, verification outcomes, partial backup results, and hidden-state alerts are either collapsed into generic labels or omitted.

Priority legend

P0 Safety, trust, or wrong-target risk. Ship before broad adoption.

P1 High-frequency friction or recovery gap. Ship in the next product pass.

North-star journey

The app should guide a developer from “What is this?” to “I know exactly what is safe to do next,” without forcing them to infer state from colors, hidden scope, or raw implementation terms.

P0 — Fix trust and safety contracts first

These issues can make a user believe the wrong thing, act on the wrong workspace, or trigger a destructive security operation without an adequate review.

1. Never say “Ready” before an authoritative baseline

P0

Cold launch creates real workspaces as unknown/unavailable, but the aggregate headline returns “Ready” whenever there is no request error. The status item independently turns amber. Manual refresh also increments the visible observation counter before a remote observation succeeds.

ObservedAppModel.swift:152-179 initializes unknown/unavailable state, returns “Ready,” and increments observationCount before the client call. StatusBarController.swift:135-169 derives a separate severity.

Change: derive headline, glyph, detail, card state, and next action from one reducer over lifecycle, freshness, quarantine, credential, setup, and operation state. Use “Not observed” on cold launch, “Showing last known state” when stale, and count only successful observations. Never let an unavailable or unknown workspace produce “Ready.”

2. Put a reviewed confirmation boundary around GitHub revocation

P0

Removing one workspace grant and disconnecting the account invoke destructive credential cleanup directly from buttons. The user is not shown the affected repositories, local unbinding, remote authorization limits, quarantine risk, or recovery path.

ObservedSettingsView.swift:154-166, 261-300 and SetupView.swift:312-337, 755-801 call removal/disconnect directly. The intended contract requires workspace-name confirmation in docs/MSW-MONITOR-MACOS26-OAUTH.plan.md:666-674.

Change: show a scoped impact review. For workspace removal, name the workspace and repositories and require typing the workspace name. For account disconnect, list all affected workspaces and require a distinct DISCONNECT phrase. State local effects, what cannot be revoked remotely, possible quarantine, and the exact post-action verification.

3. Do not mark onboarding or access complete without verification

P0

The setup copy says “Applying and verifying,” but the bind result includes verified and lifecycleRestored fields that are discarded. Any non-throwing bind is followed by markBound. System bootstrap can also set completion before the explicit final decision and without the promised identity step.

ObservedGitHubAuthorizationCoordinator.swift:620-627 ignores MSWModels.swift:338-344 verification fields. SetupView.swift:847-869 persists completion during bootstrap or “Finish without GitHub.”

Change: require verified == true per workspace, handle lifecycleRestored == false as a visible recovery state, and show a workspace-by-workspace result. Make the wizard’s final screen explicit: System ready, GitHub configured or skipped, identity configured, workspaces verified, and a deliberate Done action.

4. Make workspace scope and capabilities impossible to miss

P0

Details silently defaults to dev and has no persistent workspace selector. The only scope change is a menu side effect before opening a generic Overview. Meanwhile the server returns terminal/push capabilities, but the model retains only lifecycle capabilities, so action affordances are derived from broad state instead of authoritative permissions.

ObservedDetailView.swift:36-80, 108-120 defaults to Overview/dev. MonitorView.swift:202-218 gates integrations by running/fresh state. MSWModels.swift:234-240 exposes more capability fields than AppModel.swift:781-799 stores.

Change: carry workspace + destination in every route, put a visible workspace picker in Details, include scope in titles and confirmations, and preserve it across sections. Retain all server capability flags plus reason/recovery codes and use them in both view gates and service entry points.

P1 — Make daily operation and recovery self-explanatory

5. Show real progress and outcome reconciliation

P1

Lifecycle actions show optimistic Starting/Stopping/Restarting, then record “completed” before the following refresh confirms the result. Backup and restore collapse long-running work to “Working…” and do not surface partial restart outcomes. The protocol already has progress events.

ObservedAppModel.swift:693-764 applies and records completion before refresh. MSWModels.swift:499-508 defines progress events that are not surfaced. DetailView.swift:353-355, 508-525 shows generic work/restore UI.

Change: render a durable operation row with phase, fraction, elapsed time, affected workspace, and safe cancellation rules. Keep lifecycle operations in “Verifying” until a fresh matching snapshot. If the app or child process disappears, show “Outcome unknown,” reconcile safely, and never replay automatically.

6. Turn every failure into a next action

P1

Protocol errors carry code, recovery text, affected workspace, and retryability, but the UI mostly renders a truncated message. Quarantine reasons are visible only inside an accessibility label. Settings compresses distinct credential conditions into “Needs attention.”

ObservedMSWModels.swift:52-59 carries recovery metadata. MonitorView.swift:97-111, 218-220 exposes only a short footer/error and hidden quarantine detail. SettingsView.swift:141-149 collapses recovery states.

Change: show cause, affected scope, freshness/verification age, what is blocked, and one primary action: Retry, Setup, Reauthorize, Restart, Stop safely, Repair, Open Login Items, or Run Diagnostics. Keep the last good snapshot visible with an explicit stale banner.

7. Replace “start first” friction with truthful compound actions

P1

The documented CLI auto-starts a stopped workspace for terminal, Zed, and site entry, but the app disables all three unless already running. “Open Terminal” appears as passive next-action text rather than the useful primary button. Site is fixed to port 3000.

ObservedMonitorView.swift:170-212 gates actions on running/fresh state. AppModel.swift:214-299 rejects stopped workspaces. The documented behavior is in docs/MSW-CHEATSHEET.md:171.

Change: make the card’s best next action a button. Use “Start dev and open Terminal,” “Start and open in Zed,” and “Start and open site,” each with an effect preview and progress. Add project-path and favorite/active-port selection; retain a separate no-start URL probe.

8. Make Details and Settings one coherent navigation system

P1

Activity and Repositories both open generic Details; the detail selection always starts at Overview. Settings exists both as the native Settings scene and a separate custom window. Independent detail requests share one loading flag, error, and maintenance message.

ObservedMonitorView.swift:119-126, 208-211 routes named actions generically. MSWMonitorApp.swift:8-12 defines a Settings scene while StatusBarController.swift:92-104 creates another window. AppModel.swift:100-105, 385-580 shares request state.

Change: use typed deep links for section and workspace, remove duplicate Settings presentation, and give each section its own request generation, loading state, timestamp, stale indicator, error, and retry. Preserve cached data under “Last known / Updating” rather than replacing context with a spinner.

9. Make backup and restore honest and reviewable

P1

The UI says backups contain “workspace data and diagnostics only,” but the documented archive includes code, Docker images/volumes, databases, guest credentials, and VM state. Selecting a directory starts the backup immediately. Restore accepts a file and a generic phrase without a preview or structured result.

ObservedDetailView.swift:325-373, 411-429 starts backup after a directory pick and uses a generic restore sheet. MSWOperationService.swift:163-185 retains backup stopped/restarted lists but discards restore detail. The archive contents are documented in docs/SETUP-GUIDE.md:281-299.

Change: preview destination, sensitive contents, required space, running workspaces, stop/restart effects, archive generation, checksum, and rollback behavior. Afterward show each workspace’s outcome, warnings, and next safe action. Distinguish rolled back, rollback uncertain, and no mutation.

10. Make GitHub setup explicit, resumable, and safe

P1

After authorization, the first installation is silently seeded into every workspace; an enabled but incomplete workspace can be omitted from Apply; closing Setup cancels the session and clears drafts. “Read + write” hides the guest-read/host-only-push trust boundary.

ObservedSetupView.swift:538-575, 614-688, 741-752 filters incomplete drafts, seeds owners, and clears authorization on disappearance. SetupView.swift:401-408 labels the mode “Read + write,” while docs/GITHUB-SETUP.md:5-10 describes separate roles.

Change: keep “Choose an owner” until explicit selection, block Review while any enabled workspace is incomplete, retain drafts/session across window close, and provide “I’ve installed it — Refresh.” Rename modes to “Read in VM” and “Read in VM + push from this Mac,” with a visible two-grant preview.

11. Add opt-in background notifications with deep links

P1

This is a menu-bar monitor: its primary surface is hidden most of the time. The product plan calls for opt-in categories and deduplicated alerts for sustained unavailability, quarantine, lifecycle loss, long-operation completion/failure, backup failure, and credential deadlines, but the source has no UserNotifications implementation or notification controls.

ObservedA scoped search of app/MSWMonitor/Sources, tests, and UI tests found no UserNotifications, UNUserNotification, or authorization implementation. The intended contract is docs/MSW-MONITOR-MACOS26-OAUTH.plan.md:345, 737-747.

Change: add Settings categories with permission requested only when a category is enabled. Deduplicate by workspace/event/generation, suppress polling noise, include a deep link to the affected workspace/section, and keep repository content, usernames, tokens, and stderr out of notifications.

P2 — Polish after the contract is fixed

P2

The menu-bar item uses red/orange severity, while workspace state text and credential labels use inconsistent neutral/orange treatment. Introduce one icon-plus-label status badge with stable red/orange/green/neutral semantics; keep text and shape alongside color.

StatusBarController.swift:137-168; MonitorView.swift:155-168, 223-238.

Make sizing and metrics feel native

P2

Add scrolling or content-fitting to the 410×600 popover, persist secondary window frames, add detail minimum sizes, and replace String(describing:) metrics with named values, units, and observed-at timestamps.

What is already working

Safety foundations

Quarantine and freshness gates are fail-closed in the model; pending lifecycle/push plans are invalidated when state becomes unsafe. Push and restore require explicit phrases and initially focus Cancel.

Native interaction base

The app uses standard SwiftUI controls, a real status item, a transient production popover, reusable windows, tooltips, keyboard shortcuts for Refresh/Quit, and named workspace accessibility groups.

Unit confidence

The focused unit suite passed 38 tests with zero failures, including authorization, quarantine, stale-plan cancellation, protocol validation, backup safety checks, and workspace URL validation.
